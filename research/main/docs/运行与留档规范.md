## GPU 使用

- 训练或 GPU 推理优先使用当前可申请范围内尽可能多的 GPU，以缩短完成时间；默认申请单节点可用的最大 GPU 数。
- 每次扩大卡数前，按模型显存、通信开销、全局 batch size 和集群队列情况确认实际效率。若只能使用较少卡或缩容，必须在运行记录中写明原因。
- 不在登录节点运行 GPU 计算。所有 GPU 工作通过 Slurm 提交，并保留提交脚本和 Slurm 标准输出/错误日志。
- 同一比较中的条件使用相同 GPU 数、模型版本、数据版本和主要推理/训练参数；如有例外，必须在结果报告中说明。

## 每次运行必须留档

每次 CPU 或 GPU 运行分配唯一 `run_id`，在 `outputs/runs/<run_id>/` 留存以下文件：

| 文件 | 内容 |
|---|---|
| `manifest.json` | run_id、阶段、目的、发起时间、操作者、Git commit、主机、Slurm job ID、GPU/CPU/内存资源、环境模块和软件版本 |
| `config.resolved.yaml` | 完整解析后的模型、数据、推理或训练配置；不可只保存模板 |
| `input_manifest.json` | 数据版本、样本 ID 列表或不可变索引、模型/processor/tokenizer 版本、提示词版本及文件哈希 |
| `command.txt` | 实际执行命令；Slurm 工作需同时保存 `submit.sbatch` |
| `logs/` | 标准输出、标准错误、关键进度、异常和重试记录 |
| `outputs/` | 原始模型输出、选项概率、checkpoint 指针或其他直接产物 |
| `summary.json` | 完成状态、耗时、样本数、核心指标、失败数、产物哈希及下一步判断 |
| `report.md` | 人工可读的结果、解释、偏离计划之处和可复现步骤 |

每次数据生成、筛选、人工审计、统计分析和绘图也遵循同一规则。人工操作至少记录操作者、日期、样本范围、判定标准和结果。

## 版本与存储

- 代码、配置、提示词、运行脚本、清单、摘要、结果报告和进展报告均提交到 Git；每个独立文件或模块修改后尽快提交。
- Git 拉取与合并依 `research/项目规范/版本管理规范.txt` 使用默认 merge 策略，不显式传入 `--no-ff`、`--ff` 或 `--ff-only`。提交前在进展报告或运行档案中记录本次同步的 commit 范围。
- 需要绑定代码的运行必须以 `PINNED_COMMIT=$(git rev-parse HEAD)` 取得完整 40 位小写 commit，并把该完整值写入 `MOPD_EXPECTED_CODE_COMMIT`、run manifest 和逐条 `code_commit`。不得手抄 `git rev-parse --short HEAD` 或日志中的 7–12 位缩写。
- 提交前先在登录节点检查 `[[ "${PINNED_COMMIT}" =~ ^[0-9a-f]{40}$ ]]` 和本次运行所依赖的 tracked files 无未提交修改；Slurm/runner 继续在模型载入前精确比较完整 HEAD，并在运行各阶段复查关键文件。
- 需要排队或运行期间继续 Git 协作的正式作业，必须从该完整 commit 建立独立 detached worktree。使用 `eval "$(research/main/code/utils/create_pinned_run_worktree.sh "${PINNED_COMMIT}" "${WORKTREE}")"` 设置 `MOPD_CHECKOUT_ROOT`、`MOPD_EXPECTED_CODE_COMMIT` 和 `MOPD_RUNS_ROOT`；提交对应 worktree 中的 `.sbatch`，不得让作业回读持续变化的共享 `main`。
- 固定 worktree 只承载代码与已提交的冻结输入。run archive 必须写入 `MOPD_RUNS_ROOT/<run_id>/` 的持久目录并在提交作业前初始化，不能只写入可能被清理的 worktree。作业结束后先补齐并提交 archive，确认可复现证据完整后才能移除 worktree。
- 本地模型的 revision 字符串只是声明。正式作业必须在首次模型加载前用已提交的 revision 表和完整文件 SHA-256 inventory 重验当前模型目录，并把排他写入的 `model-asset-gate.json` 留在 run archive；缺失、额外或哈希不一致时不得启动 GPU rank。
- 数据集、模型、checkpoint 或原始日志若因体积无法提交，也必须保存不可变存储位置、大小、SHA-256 哈希、生成命令和对应 `run_id`。不得以“文件过大”为由省略可追溯记录。
- 任何清理、覆盖、重跑或人工修订必须先记录原 run_id、原因和影响范围；保留原始产物或其可访问指针。
- `进展报告/` 记录阶段性状态、决策和阻塞项；`outputs/runs/` 记录逐次运行事实。二者不能互相替代。

## 最低验收

运行完成前必须检查：输入和配置已冻结、运行信息完整、日志无未解释错误、输出可读取、summary 与 report 已写入。缺少任一项的运行只能标记为未归档试运行，不得用于论文结论或正式比较。
