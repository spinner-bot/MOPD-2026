1.1 verl 的四个角色（只需要知道这四个）

名字通俗解释在本项目里
actor被训练的那个模型，负责算 loss、反传、更新学生（整图）
rollout用 vLLM 快速生成回答的推理引擎，权重和 actor 同步学生生成 on-policy 轨迹
ref冻结的参考模型（原本用于 KL 正则）被"征用"成了教师
critic价值网络（PPO 用）本方法不用（adv_estimator: grpo 会关掉）

最关键的一个认知：Vision-OPD 没有新造一个教师模型类。它直接复用了 verl 里本来就有的 ref_module（ref 策略），把它当成教师，再把它的权重用 EMA 慢慢往学生那边拉。所以"两个教师"在工程上就是"两份额外的模型权重副本"——这对我们的双教师方案是决定性的：增删教师的成本是显存，不是架构。

def build_record(item, data_dir):
    return {

一张表里同时存了两张图：images 给学生，bbox_images 给教师。训练时教师侧只是"读另一列"，不需要在训练中做裁剪或图像变换——裁剪、放大、画框全部在数据准备阶段离线完成。这是这套代码工程上最省事的设计，也是它训练开销能压到接近普通 OPD 的原因。

3.1 clean_question() 为什么要把提示删掉

REMOVE_HINT = ("Only focus on the objects inside the red bounding box in the image "
               "to answer this question.")

def clean_question(problem):
    text = problem.replace("<image>", "").strip()
    text = text.replace(f"\n\n{REMOVE_HINT}", "").replace(REMOVE_HINT, "")
    return text.strip()

红框提示是训练期的脚手架：它告诉学生"注意这个框"。但评测时不会给你框，所以 extra_info.question 里存的是剥掉提示的原始问题——评测脚本用的就是这一列。注意 prompt 字段里保留的是带提示的版本，两者并存，不要混用。

复现核对点：如果你发现自己的评测分数远高于论文，第一嫌疑就是评测时误用了 prompt（带红框提示）而不是 extra_info.question。模型被提前告知了看哪里，分数会虚高。

6.1 EMA 那十几行到底在算什么

verl/workers/actor/dp_actor.py:134 _update_teacher()
update_rate = self_distillation_cfg.teacher_update_rate     # 0.05
for teacher_param, student_param in zip(self.teacher_module.parameters(),
                                       self.actor_module.parameters()):
    student_data = student_param.data.to(device=teacher_param.device)
    teacher_param.data.mul_(1.0 - update_rate).add_(student_data, alpha=update_rate)
    # 等价于：teacher = 0.95 * teacher + 0.05 * student

逐参数做的移动平均。注意它和 Adam 的 EMA 恰恰相反：这里 0.95 的权重给旧教师，所以教师变化极慢——大约 20 步才追上学生的 1/e。

可操作结论：teacher_update_rate 是这套代码里最便宜、最值得试的旋钮之一。0 等于冻结教师（论文 Table 3 里 79.40），0.05 是默认（79.68），调到 0.2 以上就要小心崩塌。做参数实验时从它开始，一天能跑完，风险低。

6.2 progressive 模式（代码有、论文没用）

teacher_regularization="progressive" 时，教师不是每步 EMA，而是每 teacher_update_interval 步硬拷贝一次学生权重。对应 dp_actor.py:158-174。论文里没测这个模式，但它的语义和 CRISP 的"教师每 50 步刷新"完全一致——这是我们做对照实验时可以直接复用的现成开关。

7.2 第二遍：教师前向（不传梯度）

    "input_ids": model_inputs["teacher_input_ids"],    # 教师提示（换成裁剪图）
    "attention_mask": model_inputs["teacher_attention_mask"],

        teacher_inputs, ...,
        topk_indices=student_topk_indices,              # ★ 用学生的 top-K id 取教师 logits
        module=teacher_model,                           # ★ 换模型，其余逻辑复用

这段是整个代码最漂亮的地方：_forward_micro_batch 是同一个函数，只是传了不同的 module、不同的 input_ids、不同的图像，外加 topk_indices 让教师"照着学生的候选词表"取 logits。于是两遍前向得到严格可比的分布对，还省掉了对教师做 top-k 排序的开销。

7.4 add_tail() 那行数学（论文里只有一句话，代码里有三行）

def add_tail(log_probs):
    log_s = torch.logsumexp(log_probs, dim=-1, keepdim=True)   # log(Σ p_i)，i 取 top-100
    log_s = torch.clamp(log_s, max=-1e-7)                      # 防止数值上 ≥ 0
    tail_log = torch.log(-torch.expm1(log_s))                  # log(1 - Σ p_i)
    return torch.cat([log_probs, tail_log], dim=-1)            # → [..., 101]

目标是把"剩下没进 top-100 的那些词的概率总和"压成一个额外的桶，拼在第 101 位。expm1/log1p 这类函数是为了小数值精度——如果直接写 log(1 - exp(x))，当 x≈0 时会损失全部有效数字。这就是论文说的"tail-probability term"。

注意 distillation_add_tail 的默认值是 True，而 scripts/run_vision_opd.sh 没有显式设置它。所以论文的 K=100 实际对应的是101 维分布。如果自己实现时漏了这个桶，两个分布都不归一化，KL 会算错——而且是静默地算错。

if rollout_is_weights is not None:
    weighted_per_token_loss = weighted_per_token_loss * rollout_is_weights

两处校正解决同一个问题：生成回答的模型和算 loss 的模型不是同一个时刻的权重（vLLM 引擎和 FSDP 训练副本有偏差，mini-batch 还会切分）。ratio 把损失按"现在的学生比生成时更像/更不像这个 token"加权，is_clip=2.0 截断极端值防止爆炸。

08一次训练步的完整时序One training step, end to end

把前面所有零件串起来。All the pieces in order.

① ray_trainer 从 parquet 取一个 batch（96 条）
       ↓
② rollout（vLLM）对每道题生成 8 条回答，共 768 条轨迹
       ↓                                  ← 学生侧：整图 + 红框
③ 打分：有没有标准答案？—— Vision-OPD 不需要（reward_fn 被关掉）
       ↓
④ _maybe_build_self_distillation_batch()
     把每条轨迹原样接到"教师提示 + 裁剪图"后面
     产出 teacher_input_ids / teacher_multi_modal_inputs / self_distillation_mask
       ↓
⑤ 切 mini-batch，进 dp_actor
       ↓
⑥ 学生前向 → log_probs + topk_logps + topk_indices
       ↓
⑦ 教师前向（no_grad，同一个函数换 module/输入/图）→ teacher_topk_logps
       ↓
⑧ compute_self_distillation_loss：add_tail → JSD → IS 校正 → 按 mask 平均
       ↓
⑨ 反传、optimizer.step()
       ↓
⑩ teacher = 0.95×teacher + 0.05×student   （_update_teacher）
       ↓
⑪ 下一个 batch

一个可以自查的数字：每步 96×8=768 条轨迹，每条最多 1024 token，教师与学生都要过一遍 → 单步约 1.5M token 的两次前向。这就是为什么代码要开 param_offload、optimizer_offload、gradient_checkpointing，也是为什么 batch 只能开到 96 而不是几百。

09要加第二个教师，改哪里Where a second teacher plugs in

这是读这份代码对我们最实际的用处。The practical payoff for our project.

按数据流顺序，总共要改 5 处，每处都很小：

#位置改什么难度
1prepare_data.py 的 build_record加一列（例如 concise_prompt 或 teacher2_images），让第二个教师有输入低
2actor.py 的 SelfDistillationConfig加 teacher2_* 一组字段（来源、正则化、更新率、image_key、权重）低
3ray_trainer.py:1279 视觉教师分支循环里再拼一份 teacher2_input_ids 等 5 个张量中
4dp_actor.py:1012再跑一遍教师前向，得到 teacher2_topk_logps低（复制粘贴）
5core_algos.py:1085把两个教师的损失组合起来（加权和 / 门控 / 冲突仲裁）高——这里是创新点所在

前四处是工程，第五处才是科研。而第五处恰恰是唯一没有现成答案的地方：两个教师的逐 token 分布p_T1、p_T2和目标学生p_S构成一个三角，你可以选"平均成单一目标再蒸馏"、"各自蒸馏再相加"、或者"按 token 决定听谁的"。这三种选择的差别，就是论文要讲清楚的东西。

9.1 三个现成可用的实验旋钮（不用改代码）

  • teacher_update_rate：0 = 冻结教师，0.05 = 默认，0.2 = 激进跟随。直接改脚本变量。
  • alpha：0 / 0.5 / 1 分别对应 forward KL / JSD / reverse KL，对应论文 Table 4。
  • MAX_RESPONSE_LENGTH：512 与 1024 的对照，对应论文 Table 5。这也是我们做压缩实验时最该先摸清的耦合点——把长度压到 256 会发生什么，目前没人知道。

不要一上手就改 loss。导师说的是"改关键参数看影响"。正确顺序是：先用默认配置跑通一次 → 改 teacher_update_rate 和 alpha 各跑一次 → 观察 self_distillation/raw_jsd_token_mean 和 self_distillation/num_distill_tokens 两条曲线的形状 → 再决定动哪。这两个指标决定了"你到底在蒸馏多少个 token"，是诊断一切的入口。
