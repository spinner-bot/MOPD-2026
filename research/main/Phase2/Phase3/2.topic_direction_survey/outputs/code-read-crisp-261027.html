CRISP 代码拆解Teaching verl to compress its own reasoning

CRISP does not fork verl — it wraps it. A self-contained package under workspace/src/self_distill_hybrid/ swaps in its own trainer and worker, then reuses verl's FSDP actor, sglang rollout and HybridEngine unchanged. This report follows one training step end to end.

CRISP 没有改 verl，而是在外面套了一层：自己写了一个 trainer（opsd_trainer.py）和一个 worker（opsd_worker.py）， 底下照常调用 verl 的 FSDP actor、sglang 推理和 HybridEngine。本报告沿着一步训练，把数据、两次前向、reverse KL、教师刷新全部走一遍，最后和 Vision-OPD 的代码做逐项对照。

01先纠正一个预期：它不是"改了 verl"A wrapper, not a fork

为什么这个仓库里还有个 miles/？到底跑的是哪个？Two frameworks in one repo — which one runs?

03数据：一条样本，两个提问One response, two prompts

"教师更简洁"在数据里是怎么表达的？Where does the conciseness live?

workspace/src/data/prepare_length_prune_data.py
def build_teacher_prompt_concise(question):
    cfg = _PROMPTS["length_prune_teacher"]
    content = cfg["prefix"] + question + cfg["suffix"]
    return json.dumps([{"role": "user", "content": content}])

教师提示的原文在 workspace/config/prompts.json 的 length_prune_teacher 字段：

"Solve the following math problem concisely and correctly. Be direct — avoid
unnecessary elaboration, redundant steps, or restating the problem. Focus only on
the key reasoning steps needed to reach the answer.

The last line of your response should be of the form Answer: $Answer ..."

所以 CRISP 的"教师"到底是什么：同一份权重、同一个问题，只是提示前多了一段"要简洁、别废话、只写关键步骤"。没有第二个模型，也没有标准答案。这就是它和"用 GPT 生成短答案再 SFT"的根本区别。

04训练主循环：五步走The fit() loop

一步训练里发生了什么？What happens in one step.

# ⑤ 每隔 50 步，把学生权重重拷贝给教师

self.checkpoint_manager.update_weights()

第 ① 步是整个方法的核心动作：同一道题，用两句不同的话去问。学生被问"一步步解"（原提示），教师被问"简洁地解"（加了指令的提示）。两个模型输出的是同一条回答（学生写的），所以可以逐 token 比较。

4.1 为什么第 ③ 步"验证但不过滤"值得单独说

绝大多数 RL 方法（GRPO/DAPO）会丢掉答错样本，只用答对的。CRISP 全部保留——因为它不需要"答对"这个信号，它只需要"教师在这里更简洁"。答错的轨迹一样有压缩价值。

注意 sleep_replicas() 那一行：sglang 推理引擎和训练前向共享同一批 GPU。生成完必须让推理引擎"睡下"（释放 KV cache 与权重），否则训练前向会 OOM。代码里 train_opsd.sh 顶部那段长注释专门讲了这个：不能开 expandable_segments，否则 sglang 的 torch_memory_saver 会拒绝初始化。这是"改关键参数"时最容易踩的雷。

05关键机制：两组输入怎么对齐Keeping teacher and student aligned

教师提示更长，怎么保证逐 token 比较时不错位？How alignment is guaranteed.

workspace/src/self_distill_hybrid/sd_verifier.py:347 build_opsd_batch()
for t_prompt, s_prompt, response_text in zip(teacher_prompts, student_prompts, responses):
    t_seq = _tokenize_sequence(t_prompt,   response_text, tokenizer, max_length, pad_token_id)
    s_seq = _tokenize_sequence(s_prompt, response_text, tokenizer, max_length, pad_token_id)
    if t_seq is None or s_seq is None:
        skipped += 1        # ★ 任何一边超长，整条丢掉
        continue
    teacher_seqs.append(t_seq)
    student_seqs.append(s_seq)

核心不变量：教师序列 = sd_prompt + response，学生序列 = sft_prompt + 同一条 response。 两边的 response token 完全相同，只是前面接的提示不同、长度不同。

这个不变量靠三道防线保证，worker 里那行 assert 只是第三道：

  1. SelfDistillDataset.filter_overlong_prompts：载入时就丢掉教师提示超长的样本；
  2. _tokenize_sequence() 返回 None 就整条丢弃——绝不允许只截断一边；
  3. opsd_worker.py:295 的 assert teacher_logits.shape[0] == student_logits.shape[0]。

如果这个 assert 挂了，报错信息会直接告诉你去看 data.max_prompt_length 和 opsd.sft_max_length。这是这份代码里写得最好的一条错误信息，值得学习：它不但报错，还给了下一步查哪里。

5.1 loss_mask 在标什么

teacher_loss_mask: [0,0,0,...,0, 1,1,1,...,1]
                   └─ 提示部分 ─┘ └─ 回答部分 ─┘
student_loss_mask: [0,0,...,0, 1,1,1,...,1]
                   └─ 更短的提示 ┘ └─ 同一段回答 ─┘

只在回答部分算损失，提示部分全部屏蔽。因为两边的提示本来就不同——比提示没有意义。

和 Vision-OPD 的 top-100 有什么不同？How it differs from Vision-OPD's top-K.

    "jsd":        (self._compute_jsd_loss,         self._compute_jsd_loss_liger),
    "reverse_kl": (self._compute_reverse_kl_loss, self._compute_reverse_kl_loss_liger),
}

这里没有 top-K。两遍前向都返回完整词表的 logits（(N_resp, vocab)），逐 token 算完整分布。为了不炸显存，实现上用 chunk_size=128 把 token 分块处理，每块算完立刻 del 掉中间张量。

6.1 reverse KL 的写法

KL(p_S ‖ p_T) = Σ_x p_S(x) · [ log p_S(x) − log p_T(x) ]
opsd_worker.py:688 _compute_reverse_kl_loss()

注释里写得很直白，值得原样记住：

"""This is "mode-seeking": the student concentrates probability mass on the
teacher's high-probability tokens, which encourages the student to adopt the
teacher's concise reasoning style without spreading probability over tokens
the teacher assigns low weight to."""

为什么这里必须是 reverse KL，而 Vision-OPD 用 JSD——两篇的代码各自写了原因，而且互相印证：

· CRISP 的教师更简洁，学生要"收缩"到教师的模态上 ⇒ 需要 mode-seeking ⇒ reverse KL。

· Vision-OPD 的教师和学生能力相同、只是视角不同 ⇒ 不需要收缩，对称的 JSD 更好（论文 Table 4 实测高约 1 分）。

结论：散度的选择不是风格问题，是由"教师相对学生是什么关系"决定的。我们的双教师如果一个是"看得到证据"、一个是"说得简短"，那它们和学生的关系就同时包含"对称"和"收缩"两种——这正是需要仲裁的地方，也是论文最好的立论点。

6.2 JSD 分支也实现了（虽然没用作主实验）

opsd_worker.py:498 _compute_jsd_loss()
m_log_probs = (beta * t_probs + (1.0 - beta) * s_probs).clamp(min=1e-8).log()
kl_t = (t_probs * (t_log_probs - m_log_probs)).sum(-1)
kl_s = (s_probs * (s_log_probs - m_log_probs)).sum(-1)
jsd_chunk = beta * kl_t + (1.0 - beta) * kl_s

代码里 USE_LIGER=true 时走 liger 的融合实现（省显存），否则走上面这段手写版。两版都应该给出同样的数——test_opsd_jsd.py 就是干这个的，可以直接跑来验证自己的理解对不对。

07教师刷新：硬拷贝，不是 EMAHard copy, not EMA

"教师每 50 步刷新"在代码里是哪几行？Where the 50-step refresh lives.

opsd_trainer.py:551 _update_teacher_weights() → opsd_worker.py:53 update_teacher()
def update_teacher(self):
    with torch.no_grad():
        for p_student, p_teacher in zip(student_params, teacher_params):
            if p_student.shape != p_teacher.shape:
                raise ValueError("update_teacher shard mismatch")
            p_teacher.data.copy_(p_student.data)     # ★ 直接覆盖，不是加权平均

和 Vision-OPD 的 teacher = 0.95*teacher + 0.05*student 对比，这里是每 50 步整体覆盖一次：

CRISP     : teacher ← student            （每 50 步，一次性跳跃）
Vision-OPD: teacher ← 0.95·teacher + 0.05·student  （每步，缓慢跟进）

两者语义不同，不能混用：CRISP 的教师相当于"学生的周期性快照"，两次刷新之间是完全冻结的；Vision-OPD 的教师则连续地跟着走。CRISP 论文里对刷新间隔做了完整扫描（tu1/10/20/40/60/80/100），Vision-OPD 只比了"冻结/信任域/EMA"三种。如果我们要做双教师，这个"用哪种教师同步方式"本身就是一组现成可跑的消融。

7.1 一个容易忽略的细节：同步是双向的

self._update_teacher_weights()          # 学生 → 教师
self.checkpoint_manager.update_weights() # 学生 → 推理引擎（sglang）

每一步训练完都要把新权重推给推理引擎，否则下一步生成的还是旧模型的输出，on-policy 就不成立了。这也是这套代码吃显存的原因：同一时刻显存里要装 actor（带优化器）、ref（教师）、rollout（推理引擎）三份。
