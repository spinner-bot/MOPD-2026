**触发原因**：1043 冻结包提交后，Slurm `57636033` 完成 64 项调度但完整性 gate 拒绝全部模型记录，需要在不读取效果、不更改试题的情况下定位 runner 缺陷。

## 1. 可用与不可用证据

首轮 CPU preflight 通过：manifest 为冻结 SHA `10b09d122a5781df564a63cac8449d368a2d785c3fb06ba15c3887db2433bb1c`，16 张图均匹配 checksum，Qwen3.5-4B tokenizer 的 T-Q/Generic-T median 为 49/49，A/B/C/D token 为 32/33/34/35。

四个 rank 各产生 16 条 raw，64 个 `sample_id × condition` 和 schedule index 齐全；但 64/64 条的模型前向均报 `IndexError`，标准化后唯一模式为“mask 长度比 indexed tensor 长 1”。因此：

- 成功 inference 记录：0/64；
- parsed/decision 文件：均未创建；
- S、T-Q、T-QA、Generic-T accuracy/log-prob：均不存在；
- 科学解释：不允许。

这一失败只证明完整性 gate 工作，不能判断模型、G 或题目难度。

## 2. 双重证据定位根因

实际 processor CPU 检查显示每个样本包含三份同长度序列张量：`input_ids [1,N]`、`attention_mask [1,N]`、`mm_token_type_ids [1,N]`。旧 `conditional_choice_scores` 给答案标签追加一个 token 后，前两者变为 `[1,N+1]`，却原样传入 `[1,N]` 的 `mm_token_type_ids`。

Transformers 的 Qwen3.5 `get_rope_index` 会用 attention mask 同时索引 input IDs 和 modality type IDs；这与 raw 中 64/64 的 N+1/N 长度差逐项一致。根因不是图片、显存、tokenizer continuation、manifest 或某一条件内容。

## 3. 最小修复与回归门禁

runner 现把每个新增 choice token 同步标为 modality type `0`（普通文本），并在原始 `mm_token_type_ids` 不是严格 `[batch,prefix]` 时拒绝运行。新增测试用真实 torch tensor 验证：

1. model forward 同时收到 N+1 的 input、mask 和 modality type；
2. 新增位置恰为 0；
3. 原 processor 输入仍保持 N，不被原位修改；
4. A/B/C/D 四次 scoring 都执行。

该修改不接触冻结 manifest 或任何实验自变量。run1 保留完整 raw/gate/log；不能把它和重跑结果拼接。

## 4. 裁决

1043 已预先允许“门禁失败时只修配置并以同 manifest 重跑”。因此，在本修复通过全套 CPU 测试、提交并推送后，新建 run2 完整运行 16×4；仍不得先看 S 再修改题，也不得复用 run1 raw。run2 的 gate 通过前不读取条件表现。

执行后记：同 manifest run2 `57636861` 已通过 64/64 gate，并按预注册规则得到 `INGESTION_OR_RECIPE_FAILURE`；1045 为结果与主线裁决。本后记不改变 run1 的配置失败性质。

Claude code (local) 不接手此修复；其现行任务仍是 1038 的 C4-R 独立复核。
