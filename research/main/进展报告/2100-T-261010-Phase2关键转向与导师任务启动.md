## 2. 促成转向的已知背景

上一阶段中，PC0 产生了较好的数据表现；随后项目负责人和导师发现，PC0 中提供的特权信息可能过多，导致 teacher 的优势难以泛化，甚至难以蒸馏。该判断促成了原文本特权自蒸馏路线的暂停。

之后导师独立复现了 Vision-OPD 及另一篇相关论文。根据 A101 会议记录，导师在复现中观察到：使用论文提供的训练模型进行推理时，得到的数据始终比论文声称的结果低 5 个百分点以上。会议中导师同时指出，仍需核对输出判定方式、答案正确性判定模型及其他复现细节，当前不能仅凭差值直接认定论文结论错误。

因此，当前阶段的已知问题不是“Vision-OPD 已经失败”，而是需要先弄清楚：

1. Vision-OPD 的实际输出到底是什么；
2. 最终选择项是在生成早期已经决定，还是由后续推理/证据文本实质性影响；
3. 论文中的长文本输出是否包含有效视觉证据或有效推理；
4. 输出文本、答案解析方式和正确性判定方式是否影响复现结果。

## 3. A101 中与本项目直接相关的导师指示

### 3.1 关于 JEV

会议中，项目负责人提出将问题改造成适合 JEV 的输入、以 JEV 作为 teacher 并向 LLM student 蒸馏的想法。导师明确指出，直接调用 JEV 做 teacher 属于工程思路，不是当前要研究的创新点。

导师要求学习的是 JEV 的整体形式和思想，尤其是：

- 面向简单判别/决策任务，而不是无条件生成长文本；
- 结构化输出；
- 通用地处理新任务；
- 研究为什么简单判别模型在相应任务上可能更有效。

本报告不据此预先定义 Phase2 的具体方法。

### 3.2 关于 ConfTuner

会议中，导师要求继续理解 ConfTuner 的思想，并考虑其是否能为 Vision-OPD 提供研究启发。会议对该思想的口头概括是：让模型的实际准确率与模型表达的置信度相匹配，并让真实决策结果反向影响置信度判断。

当前仅能确认 ConfTuner 是导师指定的阅读与思考材料；尚未确认 Phase2 最终采用其损失、输出形式或完整方法。

### 3.3 当前明确执行任务

导师要求在短期内完成以下工作：

1. 下载 Vision-OPD 已训练好的模型权重；
2. 不需要先在完整数据集上重跑训练或完整评测；
3. 用该权重进行若干随机抽样推理；
4. 人工查看实际输出案例；
5. 判断输出中的证据信息/推理内容是否真实有效；
6. 区分有效推理、无效格式性文本以及直接给出选择项的输出；
7. 给出总体判断、占比或案例归纳，并保留支撑结论的中间输出。

导师特别强调：必须直接接触模型真实输出，不能只看论文准确率或只依赖自动摘要。

## 4. 本次任务的事实边界

### 已知事实

- 导师要求继续做 Vision-OPD 方向；
- 导师要求审计已训练 Vision-OPD 模型的实际输出；
- 审计对象是输出中的有效证据/推理与最终判别之间的关系；
- 需要人工抽样查看并提供案例；
- 研究目标包含 CVPR 时间约束，但具体投稿年份、截稿日和论文方案尚未在本报告中重新核实；
- `research/main/Phase2/` 是新阶段资料存放目录；
- 当前本地仓库已有 Vision-OPD 相关复现代码、论文材料和部分数据/资产索引，但权重的具体本地可用性尚待检查。

### 尚未确认，不得当作结论

- Vision-OPD 输出中的 reasoning 是否对答案有因果作用；
- 输出中的证据是否正确、完整或只是格式模板；
- 关闭某种输出模式后准确率是否变化；
- 论文结果低于复现结果的具体原因；
- JEV 与 ConfTuner 是否会组成 Phase2 的最终方法；
- Phase2 是否需要重新训练模型。

## 5. 执行流程与中间产物要求

本次工作按以下顺序执行，并在后续报告中逐步回填实际结果：

```text
Phase2 目录与工作树检查
→ 定位 Vision-OPD 论文、复现代码、权重与推理入口
→ 核对权重身份、文件完整性和运行环境
→ 固定抽样规则与样本清单
→ 运行少量 smoke 推理
→ 保存 raw 输出、解析输出、运行配置和哈希
→ 随机抽样并人工查看案例
→ 建立人工审计表
→ 汇总输出类型、有效证据、推理和答案关系
→ 对关键案例进行必要的反事实/对照检查
→ 形成阶段结果报告
```

除最终汇总外，必须保留：

- 输入样本清单及其来源；
- 模型权重路径、revision、文件哈希或可核验身份；
- 推理脚本、配置、prompt 和运行环境信息；
- raw 模型输出；
- 解析后的字段；
- 人工审计表及审计者/时间；
- 失败、截断、解析异常和无法判断的记录；
- 每次重跑的新 run ID，不覆盖既有产物；
- 结论与证据之间的逐项对应关系。

人工审计不得把模型自身的解释直接当作事实标签；需要区分“模型声称的证据”和“人工确认的有效证据”。

## 9. 本地预检结果

在本地工作站完成了以下只读检查：

- `reproduction/1. Vision-OPD/` 中存在论文 PDF、复现代码、推理脚本和评估指南；
- 推理入口为 `reproduction/1. Vision-OPD/code/eval/run_eval.sh` 与 `infer.py`；
- `infer.py` 通过 OpenAI-compatible API 调用已部署模型，并把模型原始文本保存到 `model_answer` 字段；
- `run_eval.sh` 默认不设置 `ENABLE_THINKING`，但 `infer.py` 支持显式传入 `--enable_thinking True/False`；
- 当前代码目录中的 `normalize_model_answer` 只定义了规范化逻辑，实际推理记录仍保留 `resp.choices[0].message.content` 原文；
- 本地 `research/main/models` 和 `research/main/data/external` 是指向远端存储的占位链接文本，不是可直接加载的本地模型/数据目录；
- 本地未发现 `Vision-OPD-4B` 或 `Vision-OPD-9B` 训练权重、合并 checkpoint 或可直接运行的 benchmark 图像资产；
- 复现目录 README 明确将本地 Windows RTX 5060 8GB 定位为代码开发环境，将 H200 服务器作为模型训练/评估环境；
- 公开 Vision-OPD 模型集合中列有 `yuanqianhao/Vision-OPD-4B` 和 `yuanqianhao/Vision-OPD-9B`，但本地尚未下载或核验这两个仓库的实际文件。

因此，导师要求的模型权重下载和真实多模态推理不能在当前本地环境中直接完成；需要使用 Leonardo/H200 或其他具备模型资产和 GPU 环境的服务器。代码、审计协议、抽样脚本和报告准备可以在本地完成。

## 10. 已建立的 Phase2 审计准备

已在 `research/main/Phase2/vision_opd_output_audit/` 建立：

- `README.md`：审计目的、目录、输入输出和大文件存储边界；
- `protocol.md`：人工审计顺序、输出分类、证据/推理判定字段和事实边界；
- `sample_and_prepare_audit.py`：基于 `sha256(seed + sample_uid)` 的确定性抽样、raw 输出保留和人工审计模板生成脚本。

该脚本不会自动判断模型解释是否有效，只负责固定样本、保存原始输出、计算原始输出哈希并创建待人工填写字段。这样可以避免把自动解析结果误写成导师要求的人工案例结论。
