## 诊断结论

GitHub 与 SSH 认证均正常。首个工作5提交 `1c0df3d` 已推送至 `spinner-bot/MOPD-2026`；随后从 Leonardo 登录节点执行 `git ls-remote`，读取到同一提交。登录节点为 `login02.leonardo.local`。因此故障不在 GitHub、SSH 密钥或仓库访问权限。

问题出在写入路径。最初只查询 `/leonardo_work` 顶层时，看到整个 Lustre 文件系统仍有大量可用空间；进一步对实际项目路径查询 `df -h /leonardo_work/AIFAC_F02_774/rqian000/MOPD-2026`，该路径所在挂载点显示容量 `1.0T`、已用 `1.0T`、可用 `0`、使用率 `100%`。用户级/组级 Lustre quota 输出没有显示独立限额，不能据此否定具体挂载点已经满载。此前报告“配额问题尚未定位”已由此次路径级查询更新。

根据项目服务器存储规范，脚本和 Git 工作树应位于 `/leonardo_scratch/fast/AIFAC_F02_774/rqian000`，数据、模型权重和大型运行结果位于 `/leonardo_scratch/large/userexternal/rqian000`。fast scratch 路径当前约 `995G/1.0T` 已用、剩余约 `30G`，足以容纳稀疏 Git 工作树和脚本，但不应用于大型模型输出；large scratch 所在文件系统约 `5.1P` 可用，作为数据/权重/运行产物区。

## 已采取的安全处置

1. 本地只提交并推送了工作5目录内文件；工作区其他既有未提交修改没有纳入该提交。
2. 确认旧项目工作路径不存在后曾尝试从 GitHub 克隆。克隆在已满挂载点失败；未删除或清理任何既有数据。一个很小的不完整/稀疏克隆目录保留在 large scratch 下，作为故障诊断中间产物，不用于正式运行。
3. 在用户指定的 fast scratch 新建稀疏 Git 工作树：`/leonardo_scratch/fast/AIFAC_F02_774/rqian000/MOPD-2026-work5`。该工作树跟踪所需 Vision-OPD eval 代码、工作5文档、提示词、项目数据清单和规范；体积约6 MB，commit 为 `1c0df3d`，Git 状态干净。
4. 数据与权重目录规划为 `/leonardo_scratch/large/userexternal/rqian000/MOPD-2026-work5-data`。数据由服务器从官方/固定版本数据源直接获取；GitHub 仅负责代码和可提交的小型文档/脚本同步。未使用 SSH/SCP 传输数据文件。

## 后续执行约束

- 不再向已满的 `/leonardo_work/AIFAC_F02_774/rqian000` 写入工作5内容；每个作业启动前确认脚本、临时文件、模型缓存、输出和日志各自落在正确 scratch 路径。
- Hugging Face/CUDA/PyTorch/VLLM 等 cache 显式指向 large scratch；scratch 本地临时目录不可假设可用，Git 操作显式使用 `/tmp` 作为 `TMPDIR`。
- fast scratch 仅放 Git 工作树、脚本和小型分析代码；运行输出、原始回答及派生大文件放 large scratch。large scratch 中的中间文件保留并带 manifest，不因任务失败自动清理。
- 后续本地提交经 GitHub 中转；服务器更新遵守项目要求使用 `git pull --no-ff`。本诊断本身不代表评测数据已经下载或全量实验已经启动。
