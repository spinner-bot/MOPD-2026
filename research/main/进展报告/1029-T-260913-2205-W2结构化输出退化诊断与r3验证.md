## 1. 当前结论

1027 的 `no_repeat_ngram_size=4` 不适用于严格 JSON。它没有修复候选筛选，反而把原本可解析的固定 schema 系统性破坏。W2 科学进度仍为零：没有 audit 全量结果、没有可进入人工审核的构造结果，也没有运行 S/T 条件。

所有列入 1028 的 screen/construct 作业现已结束：screen 全部 `FAILED`，依赖的 construct 全部 `CANCELLED`，当前无 MOPD 作业在队或运行。旧档案保持不变，仅用于失败诊断。

## 2. 直接证据

### 2.1 对照

| 档案 | generation config | blind canary | 截断 |

r2 并未因输出过长失败；其 EOS 与截断门控全部健康。失败集中在 schema 字段名，例如：

- `image_is_necesssary`、`image_is_n necessary`、`image_is_necessity`；
- `requires_unprovided_facts`；
- 缺少 `ambiguous` 的起始引号；
- `"**uncertainty**: ..."` 被生成为单个错误字段。

这些原始输出完整保存在对应 `canary/blind/rank-*.jsonl`。门控将其全部拒绝是正确行为；不得增加模糊字段名映射或宽松修复来制造通过率。

### 2.2 因果判断

`no_repeat_ngram_size` 面向自由文本去重，会禁止已经生成过的 token n-gram。严格 JSON 中字段名、标点和共同词根本来就必须按模板重复；模型为满足约束而改写 key 或破坏引号。退化与配置切换同步发生，并在互不相同的四组 canary 上复现，因果证据充分。

## 3. r3 纠正

已完成以下代码修改：

1. candidate runner 删除 `repetition_penalty` 和 `no_repeat_ngram_size` 参数及 `model.generate` 传参；
2. screen/construct sbatch 不再读取或传递这两个环境变量；
3. 保留 greedy、`enable_thinking=False`、`max_new_tokens=1536`、EOS/截断记录、严格 schema 与 fail-closed gate；
4. 保留 blind prompt 的 1–4 条不同观察、每条最多 24 词约束，以内容合约限制长度；
5. 44 项 CPU 合约测试、runner `py_compile`、两个 sbatch `bash -n` 全部通过。

对应提交：`3779577`、`c597b65`、`49352a4`。

### 3.1 排队代码漂移的追加门控

首次 r3 作业 `57568183/57568184` 提交后仍处于 PENDING，尚未执行样本。此时复核发现，旧 sbatch 只在 raw provenance 中读取启动时 `HEAD`，没有校验“提交作业时的代码”和“获得资源时的代码”一致。c2/c3 正是因此在排队期间静默采用了后来提交的 r2 参数。

## 4. 最小验证与继续条件

r3 只先重跑固定 C1 128 条链，使用新 run_id，绝不覆盖 r2 或已取消的首次 r3 档案：

- 首次提交后主动取消的归档：`20260913T2210-teacher-gap-{screen,construct}-c1-128-r3`；
- 固定代码提交后的有效验证：`20260913T2220-teacher-gap-{screen,construct}-c1-128-r3b`，construct 仅以 `afterok` 依赖 screen。

screen 必须依次满足：blind canary 8 条、blind full 128 条、audit canary 8 条、audit full 128 条。canary schema-valid rate 至少 75%，full 至少 90%，且任一阶段不得有 runner error 或截断/缺 EOS。通过后才允许构造；构造也执行同样的 canary/full 门控。

只有 r3 全链通过并核验产物后，才决定是否以相同配置重跑 fullpool。若 blind 仍因重复耗尽 1536 token，则优先改为多字段/受限枚举解码等结构化生成机制，不能恢复破坏 JSON 的 n-gram 约束。

### 4.1 r3b 最终结果

screen job `57568703` 于 2026-09-13 16:47:13–16:57:42（CEST）在 `lrdn1867` 的 4×A100 上运行，固定提交 `1d5e8cd` 校验通过。

- blind canary：8/8 valid、0 截断、0 runner error，gate 通过；
- blind full：128 条齐全，旧提交契约 122/128 valid（95.3125%），6 条 invalid JSON，其中 5 条在 1536 token 截断；
- 5 条截断均在 `visible_evidence` 内循环重复，故 completion gate 按“截断必须为 0”失败；
- audit 未运行；construct job `57568704` 被依赖自动取消，运行时间 0；
- 用 `codex/w3-hardening` 严格内容契约事后重解析为 119/128 valid（92.96875%），另拒绝重复 evidence 1 条、超出 1–4 项边界 2 条。

r3b 因而确认两点：移除 n-gram 约束修复了 r2 的字段名灾难；把预算提高到 1536 仍不足以根治约 3.9% 的确定性循环。下一版改为“首轮原始输出不可变 + 仅对失败记录使用显式紧凑 fallback + 全 attempts provenance”，不得用宽松字段映射救回。

### 4.2 r4 冻结实现

r4 已在提交 `36a569d` 实现上述方向：主尝试使用 greedy、non-thinking、768 token；只有主尝试截断或未通过当前 stage 的严格 schema/content contract 时，才以同一字段白名单执行一次 512-token 紧凑 fallback。选择结果始终是最后一次 attempt；若 fallback 仍不合格，记录照常进入 reject，不能被宽松重解析晋升。

每条 raw record 保存主尝试和可选 fallback 的原文、attempt 类型、各自 token 上限、prompt/template hash、输入/生成 token 数、EOS/截断与重新计算的拒绝原因。completion gate 不信任 runner 的 `schema_valid`，会从每次 raw output 独立提取 JSON、重跑契约，并核验 attempt 数量、触发条件、选中索引、token 配置和顶层镜像字段。这样既允许回退修复配置型长尾，又完整保留主输出失败率，后续可分别报告 `fallback_used`、`fallback_recovered` 与 `primary_truncated`，不会把回退后的通过率伪装成单次生成能力。

r4 仍只运行固定 C1 128 条。通过 blind/audit 两阶段 canary 与 full completion gate 后，才允许依赖构造；在该链获得实证前不扩 fullpool。当前 CPU 合约测试 62/62 通过，runner `py_compile`、sbatch `bash -n` 与 `git diff --check` 均通过。

### 4.3 r4 结果与 r5 修正边界

r4 screen job `57574779` 于 2026-09-13 17:21:27–17:31:33（CEST）在 `lrdn3398` 的 4×A100 上运行，固定提交 `ae9600f`。blind 修复达到预期：canary 8/8；full 127/128（99.22%），9 次 fallback 恰与 r3b 事前回放预测一致，其中 8 次恢复，5 个 primary 截断最终全部被无截断输出替换。唯一未恢复记录继续严格拒绝。

audit canary 随后以 4/8（50%）低于 75% 门槛熔断；audit full 未运行，construct `57574781` 依赖取消且运行时间为 0。6 个 audit primary 的高层标签均为 `external_required`，主要结构错误是把 JSON null 写成字符串 `"null"`（6 条）或仍为 non-qualifying 样本生成图/证据（2 条）。旧紧凑 fallback 从带 image-only 示例的空白模板重新判断，6 次仅 2 次结构恢复，且其中一次把 `external_required` 错翻为 `image_only`，以外貌推断国籍。

因此 r5 必须把“结构修复”和“重新语义判断”分开：若 primary 可解析，fallback 显式锁定其高层决定字段，只重写严格 JSON 与依赖结构；compact audit 同时给出完整 qualifying/non-qualifying 模板，消除 image-only 单侧示例诱导。gate 还需从 primary raw 独立重建这些锁定字段和 fallback prompt hash，防止 runner 声称锁定但实际提示未锁定。继续禁止把字符串 null 静默正规化；修复仍由第二次原始模型输出完成并完整留痕。

r5 已在提交 `5841e2d` 实现：blind 锁定可恢复的答案/三项判断，audit 锁定知识标签、四项布尔判断与合法 family，construct 锁定 decision/可恢复正确答案；audit primary 完全不可解析时保守锁为 `ambiguous`。runner 与 parser 都会把任何锁定字段翻转记为 `fallback_decision_mismatch`，gate 再从 primary raw 重建锁定值和两次 frozen prompt hash 独立复核。65/65 CPU 合约测试通过。为避免再次完整重跑后才发现模板问题，先运行独立 8 条 audit canary；只有该 canary 通过才建立新的 C1 全链。
