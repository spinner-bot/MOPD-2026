## 2. 新发现的三个有效性缺口

### 2.1 多答案干扰项必须保持目标基数

多目标题的正确选项是一个紧凑 JSON 数组字符串，例如 `["Ford","Acura","Suzuki"]`。如果错误选项仍是单个品牌名，四选一任务就改变了原题目标，选项长度还会泄露正确答案。

新版 construct validator 要求：当目标基数大于 1 时，每个 distractor 都必须能解释为 JSON 数组，数组长度严格等于目标基数，每项均为非空字符串。正确选项和三个错误选项按归一化后的**无序完整项集合**去重，避免只交换项目次序制造伪干扰项。重复 canonical 项仍按原始顺序和基数保存。r7b 实测后确认，JSON 数组本体与其字符串编码是等价表示；提交 `195bc05` 起两者均接受，冻结器统一编码为紧凑字符串。

### 2.2 guide 图对齐必须在生成当场检查

旧流程已在人工审核队列入口检查 `supports_next`，但构造 canary/full gate 本身只检查 guide 字段非空。这样一个 `supports_next=missing-node` 的输出会被计为构造成功，直到下游队列才拒绝，导致构造通过率被高估。

新版 runner、解析器和独立 gate 都将同一 `audit_proposal` 传入 construct validator。每个 guide 必须指向审计图中现存节点；错误在 canary 即触发 fallback 或 fail-closed。r7b raw 证明，guide 可以合理地用问题先取得一个 evidence node，例如“左侧车辆是什么品牌”；因此提交 `195bc05` 起允许 evidence、intermediate 或 answer 节点，仍拒绝 dangling target。人工审核队列复用同一校验函数，消除两套标准漂移。

### 2.3 重复答案项不能被一次原子提及误判为完整泄漏

全量 M3VQA 中存在多个实体共享同一答案值的题目，例如完整答案可能是 `["Ford","Ford"]`。旧的“每个答案组命中一个 alias”实现会让 guide 中一次 `Ford` 同时满足两个相同组，错误判为完整答案泄漏。

新版检查先按 alias group 签名计数；同一组重复两次时，单个 guide 文本中也必须出现两次匹配才算直接泄漏。它仍只负责保守、可确定的单 guide 明文泄漏，跨 guide 拼接、同义改写和间接提示继续由 100% 人工审核判断。

## 3. 实现与验证

提交 `99e477c` 同步修改：

- construct normal/compact prompt：显式给出 answer cardinality、数组格式和 graph target 约束；
- runner、离线 parser、独立 completion gate：统一传递 `audit_proposal`；
- construct validator：新增 `invalid_distractor_cardinality` 与 `guide_graph:*` 原因；
- 人工审核队列：改为调用同一个构造 validator，删除重复的下游图检查；
- 泄漏检测：按重复 alias group 的出现次数判断完整答案；
- 测试：新增错误基数、空数组项、仅换序选项、dangling target、重复答案单次/双次提及用例。

验证结果：项目固定 Python 3.11 环境下 `unittest discover` 共 75 项全部通过；5 个变更 Python 文件静态编译通过；`git diff --check` 通过。
