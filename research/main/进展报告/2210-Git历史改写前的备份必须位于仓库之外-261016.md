# 2210-Git 历史改写前的备份必须位于仓库之外

**性质**：重点文档；记录历史改写（`git filter-repo`）中关于备份位置的经验与操作规则。

**创建时间**：2026-10-16 04:51（UTC+8）  
**创建作者**：Claude Code (local)  
**触发原因**：报告 2202 执行提交作者历史改写时，虽在改写前于仓库内建立了备份分支与标签，但事后核验发现**这些备份已被改写本身一并改写，失去还原能力**。所幸同时建立了仓库外的镜像副本，才保留了退路。本文将这一教训固化为规则。

---

## 1. 规则

> **执行 `git filter-repo`（或任何全 ref 改写）之前，备份必须建立在仓库之外。**

仓库内的备份——`git branch backup/...`、`git tag backup-...`、`git bundle` 于同仓库目录内——**都会被视为待改写的 ref 而一并改写**，因此不构成有效备份。

唯一可靠的形式是**仓库目录之外的镜像克隆**：

```bash
git clone --mirror <repo> /path/outside/repo-mirror-<date>.git
```

## 2. 证据

报告 2202 的改写过程提供了直接对照。

**改写前**建立的仓库内备份：

```
backup/pre-author-fix      → c7950348   （改写前 HEAD）
backup-author-fix-20261016 → c7950348
```

**改写后**核对：

```
backup/pre-author-fix      → 358e1154   ← 已变
backup-author-fix-20261016 → 358e1154   ← 已变
```

`358e1154` 正是 `c7950348` **改写后**的对应提交。也就是说，备份指向的内容**已经被改写**，无法用于还原到改写前状态——**备份名存实亡**。

**改写前**同时建立的仓库外镜像：

```
F:/_git-backup/MOPD-2026-mirror-20261016.git
main → c7950348   （完好，未被触碰）
```

本次改写之所以有退路，**完全依赖这份仓库外镜像**。

## 3. 附带发现：`filter-repo` 的改写是确定性的

同一 mailmap、同一历史，**两次独立改写的产物哈希完全相同**：

| 原始提交 | 第一次改写产物 | 第二次改写产物 |
|---|---|---|
| `c7950348` | `358e1154` | `358e1154`（相同） |

原因：改写是原始提交内容的纯函数——`(父提交, 树, 作者, 提交者, 信息)` 经 mailmap 映射后确定唯一哈希，不含时间戳或随机量。

**这一性质带来一个容易误判的副作用**：第一次改写的中间产物会"混入"第二次改写的历史，成为其合法组成。核验引用时我一度把 `358e1154` 判为孤儿，实际它是当前历史中的一环（详见报告 2208）。

**因此判断某个提交是否失效，不能依据"它是不是我某次实验的产物"，只能依据 `git merge-base --is-ancestor`。**

## 4. 配套规则

结合报告 2202 的执行过程，归纳为四条：

1. **改写前**：`git clone --mirror` 到仓库外，并核验其 `main` 指向改写前的 HEAD。
2. **改写中**：不要依赖仓库内备份；改写工具会提示 `--force`，此时应确认外部备份已就绪而非忽略提示。
3. **改写后**：核验三件事——目标身份残留为 0、提交总数不变、工作树哈希与改写前一致。
4. **清理时**：仓库内的"备份引用"可在确认外部备份有效后删除；它们本身不具备备份价值（见报告 2208）。

## 5. 推广

本规则不限于 `filter-repo`。任何会改写全部 ref 的操作同理：

| 操作 | 是否改写仓库内备份 |
|---|---|
| `git filter-repo` | **是**（默认 `--all`） |
| `git filter-branch` | **是** |
| `git rebase` / `commit --amend` | 仅改写被触及的分支，但若备份分支共享这些提交，其指向不会变、内容仍可还原 |
| 普通 `commit` / `merge` | 否 |

**判据：该操作是否会重写提交对象本身。** 会，则仓库内备份无效。
