## 自动化链

```text
56995520: T02 四卡推理
       │ afterany
       ▼
57014469: JSON / bbox / 标签校验与 accepts/rejects 分流
       │ afterany
       ▼
57015138: 1,200 条完成性 gate（不完整即失败）
```

`afterany` 的选择是为了在 T02 成功、失败或超时后都留下可审计的结论。完成性 gate 读取校验汇总，要求观测记录数严格等于 1,200；记录不足时以非零状态失败，禁止将部分结果作为质量或吞吐依据。

这两项后处理都不占 GPU，不会在 T02 等待期间占用资源，也不会因用户离线而中断。

## 全量 GPU 方案

pilot 的质量、完整性和实际吞吐通过后，才可提交 `submit_preprocess_h_pipeline.sbatch`。该脚本在**一份**长时四卡 allocation 内保持资源并按下列顺序执行：

```text
全量 T02 → T02 确定性校验/crop 分流
        → T03 latent graph 与 guide QA → T03 校验
        → T04 选项语义复核 → T04 校验与确定性控制物化
        → T05 独立质量验证 → accepted / borderline / rejects 分流
```

每个 H 阶段保持独立 prompt、原始输出、解析输出、拒绝原因和 run archive 路径；T03 与 T05 即使使用同一固定 Qwen3.5-9B revision，也不共享提示词或输出目录。任一阶段失败会因脚本的 `set -euo pipefail` 阻断下游，避免未验证结果进入下一阶段。

该全量 allocation 不能在当前直接提交：其墙钟时间必须由 pilot 的实际吞吐确定，且必须先确认 T02 质量。这样避免用未经验证的长作业占用 GPU，也避免在 T02–T05 间重复排队。
