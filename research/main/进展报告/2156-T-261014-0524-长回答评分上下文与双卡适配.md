# 2156-T：长回答评分上下文与双卡适配

日期：2026-10-14

## 发现

全量实验保留 Vision-OPD 的 32,768 最大生成 token 设置。对 pilot 的 200 条模型输出审计发现，最长记录来自 `SC/mme-realworld`，输出为 32,768 tokens、90,143 字符。该回答没有 `</think>`、`<answer>`、`</answer>`、`Answer:`、`Final answer` 或 `Therefore` 标记，属于没有可供评分脚本直接定位的答案段落的长输出。

此边界同时影响两条评分链：

1. 答案抽取器把完整 `model_response` 连同 query 和格式信息交给 Qwen3.8-27B；此前抽取服务 `max_model_len=8192`，不足以容纳已观察到的输出。
2. Vision-OPD 原生评分先寻找 `<answer>…</answer>`，再寻找 `Answer:`，否则将全文交给裁判。上述 pilot 长回答将走全文回退分支；其本地 vLLM 调用此前未显式设置上下文长度，且每个任务只申请一张 A100。

若不处理，抽取服务可能留下 `TECHNICAL_ERROR`，原生评分也可能因上下文/KV cache 约束而失败。统计作业要求所有输入状态完整有效，因此不能把这些记录静默略过或截断。

## 调整

- 将答案抽取服务设为 `max_model_len=65536`、`tensor_parallel_size=2`，并在每条运行 manifest 中记录并行度。
- 将 Vision-OPD 原生裁判调用扩展为可选 `--judge_tensor_parallel_size`、`--judge_max_model_len` 参数；默认仍保持原有默认行为。Work5 作业显式传入双卡与 65,536 上下文。
- 两个评分数组任务均申请每任务 2 张 A100，并将并发度从 8 降为 4，即同时最多占用 8 张 GPU；其余资源和评测逻辑不变。
- 不修改 32,768 生成上限、不截断或改写回答、不改官方 judge prompt 和输出判定规则。只扩展服务可承载上下文的资源设置。

65,536 是基于已实测最长输出的保守运行配置，覆盖 32,768 输出 token 及问题/评分模板的额外输入空间。模型配置声明支持更长上下文；是否能在目标节点稳定启动，仍须由服务器上的配置验证作业确认。若启动失败，保留原始结果并继续排查资源配置，不以截断输入作为替代。
