## 3. 根因：答案项与别名混为一谈

M3VQA 官方字段语义是：

- `answers`：示例/规范答案列表；
- `answer_evals`：评测所用的**目标答案组列表**，每个子列表是一个目标项的可接受别名；
- 官方 evaluator 令 `n=len(answer_evals)`，将预测答案与每个子列表匹配，再计算集合式得分。

旧 normalized/C1 输入只保留 `answers` 为 `reference_answers`，W2 prompt 又称其为 “Reference answer aliases”。这会产生两类错误：

1. 多目标题被模型当成“任选一个别名即可”。例如 `m3vqa-data_0008198` 的完整 gold 需要 `Ford/Acura/Suzuki` 三项，旧 audit 却以 `Ford` 单项认定参考答案被图像蕴含。
2. construct validator 又要求正确选项等于 `reference_answers` 中某个单项；模型输出完整列表时被拒绝，输出单项时虽可能过旧校验却答错原题。

固定 C1-128 的真实目标基数为：1 项 54 条，2 项 20 条，3 项 23 条，4 项 16 条，5 项 15 条。**74/128（57.81%）是多目标题**，所以不能把它视为少量边角缺陷。

全量 13,125 条中另有 20 条 `len(answers) != len(answer_evals)`，且都只有一个 `answer_evals` 目标组；这些旧 `answers` 值实际落在同一个别名组内。转换器只在这一已验证形态下折叠为单目标，否则 fail-closed。

## 4. r6 construct 暴露的附加缺陷

construct 8 条 canary 的最终原因计数为：完整答案不匹配 4、明显泄漏 3、干扰项结构错误 1、fallback 决策锁不一致 1。逐条原始输出还证明：

- audit fallback 有时原样返回 `E1`、`E2` 或 `replace with …` 占位文本，旧 validator 只检查非空，导致伪证据通过；
- construct fallback 会锁定 primary 中已经被 validator 判错的 `correct_answer_text`，使第二次尝试无法修复；
- 旧泄漏检查把任一 atomic answer 的出现都当成完整 final answer 泄漏。对于多目标题，单个 atomic item 可能是真正 intermediate；应按完整目标组判断自动泄漏，再交由人工检查跨 guide 和语义泄漏。

这些问题都必须保留 fail-closed 立场：修复精确语义，不能删除唯一答案、外部知识、R/PR、guide 或泄漏门槛。

## 5. 已实现的 r7 输入与代码契约

提交 `5c0ec1d` 实现：

1. candidate 必须同时含 `reference_answers`（每个目标组的 canonical item）、`reference_answer_alias_groups`（逐项目别名组）和可重算的 `canonical_answer_text`；旧输入直接拒绝。
2. 单目标选项保持普通字符串；多目标完整选项使用确定性紧凑 JSON 数组字符串，保留顺序与重复项。
3. audit 明示必须判断完整答案的每个目标项；construct 必须逐字复制 canonical 完整选项。
4. construct fallback 只锁定合法 decision，并从输入锁定 canonical answer，不再继承已知错误答案。
5. audit validator 拒绝 `E1/E2/evidence 1/2/replace with` 等占位证据与图节点。
6. 自动泄漏检查按单个 guide 是否覆盖全部答案组判断；更隐蔽和跨 guide 的泄漏仍保留给 100% 人工审核。
7. gate 同步重建新增字段、prompt hash 与 fallback lock；审核队列显式显示 answer groups 和 canonical 完整答案。

72 项 CPU 测试全部通过，覆盖多目标 canonical option、旧单组折叠、raw join/图像 ID 不一致、占位证据、fallback 输入锁定以及 evidence firewall。

CPU 运行档 `20260914T0152-m3vqa-answer-contract-c1-128` 已将同一 C1-128 全量重建：128/128 成功、0 reject，双跑字节一致、128/128 通过新版 candidate validator，输出不含官方 evidence/URL/posthoc 字段。

## 6. r7 重启顺序与停止条件

1. 只对修复后的同一 C1-128 建立新 screen→construct run_id；仍固定 4×A100、48 小时、non-thinking、greedy、primary 768 + compact fallback 512。
2. screen canary/full 和 construct canary/full 必须按现有 gate 通过；任何占位证据、答案项缺失、canonical option 漂移或 runner error 均 fail-closed。
3. r7 screen 的标签分布是第一份可解释的 C1 原问题适配率；与 r6 的 13/128 不做数值拼接。
4. 只有 r7 construct full 通过，才生成机器候选审核队列；所有 `human_*` 字段继续留空。
5. 只有 C1 完整链通过，才用同一答案转换器重建 `exp-fullpool` 四块并提交扩量。不得直接复用旧 fullpool JSONL。

即使 r7 产率很低，也只能说明“M3VQA 原题 + 完整答案”不适合闭世界 teacher-gap；不能据此否定这些图片的 R/PR affordance。若原问题候选不足 136，按 1031 启动图像优先重构支路。
