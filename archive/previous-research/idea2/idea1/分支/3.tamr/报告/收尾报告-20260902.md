# tamr 分支收尾报告

---

## 一、分支目标回顾

核心思路：不同任务需要不同的模态组合，提出任务级（而非 token 级）的教师路由——通过一个轻量任务分类器预测当前任务类型，据此选择 VL 教师 / Text 教师 / 双教师等权组合。相比 token 级路由（如 H-OPD），计算开销更低（<1%），可解释性更强（知道为什么选某个教师）。

## 二、已完成工作

1. **核心算法模块**：`tamr_distillation.py`，包含：
   - `LightTaskClassifier`：轻量级任务分类器（基于 prompt embedding）
   - `task_routing_weights`：根据任务类型给出两教师权重
   - `tamr_distillation_loss(student, vl_teacher, text_teacher, task_type, config)`：主损失函数
   - `TAMRDistillation` 封装类（支持自动任务分类）
2. **单元测试**：`test_tamr_distillation.py`，覆盖任务路由权重、分类器、各任务损失等逻辑。
3. **sync 部署包**：`sync/` 含 `deploy.sh` + 指令集。
4. **分支概述**：`分支概述.md`。

**未完成**：尚未集成进 `dp_actor.py` 训练框架；任务分类器需在真实训练数据上预训练或联合训练。

## 三、关闭原因

经 2026 年 8-9 月文献调研，发现与 tamr 思路高度重合的工作已存在：

- **Lightning OPD 2.0**（arXiv 2607.28449）：显式地将 advantage 分解为跨教师分歧项与 reference-anchoring 项，实现了任务/样本级的差异化教师处理。
- **Multi-Teacher Mixture-of-Experts 系列工作**（如 arXiv 2509.00039, 2502.18510, 2510.18680）：任务级/样本级的教师路由是 MoE 文献中的成熟思路，在 OPD 框架下已有对应实现。

"按任务选教师"本质上是 MoE routing 在 OPD 中的直接应用，方法创新性较弱；而 Lightning OPD 2.0 已经在 OPD 内部实现了更细粒度的跨教师分歧处理，tamr 的 task-level 路由在粒度上反而更粗。

## 四、保留资源

- `test_tamr_distillation.py`：单元测试范式。
- `sync/`：部署包范式。
